What it does

The kit runs inside your app, on Upstash or on your own Supabase Postgres. It covers three places where a small app tends to get an unexpected bill: a route that anyone can hammer, an AI call with no per-user ceiling, and a checkout button that creates a new Stripe session on every refresh.

Rate limits (lib/ratelimit.ts). Five presets: anonymous IP, signed-in user, AI route, auth/OTP, and checkout. They run on Upstash's sliding window or a Supabase Postgres counter. Over the limit, the route returns 429 with Retry-After. If the limiter backend is down, it returns 503 by default; you can switch that to let traffic through.

AI spend cap (lib/spend-cap.ts). A dollar ledger per user per month, priced from each response's token usage, including cached tokens, cache writes at their lifetime's rate where the usage data gives the split (OpenAI 30-minute and 12-hour, Anthropic 5-minute and 1-hour), and streams. A stream cut off before its final usage is charged at least the up-front estimate. It warns at 80% and is designed to block the next AI call at 100%.

  • The price table covers 17 current OpenAI and Anthropic models, last checked 18 Oct 2026.
  • A model that isn't in the table is refused, not counted as $0.
  • Each call reserves its estimated cost first, so parallel calls can't all slip under the cap at once.

Checkout guard (lib/checkout-guard.ts). For the same user and cart within 10 minutes, it hands back the open Stripe Checkout Session instead of creating another. It adds idempotency keys and a per-user limit, and dedupes webhooks on event.id with a pending/completed status.

SQL (sql/001_spend_caps_kit.sql). Four tables with RLS on, and two security definer functions with a pinned search_path that only your server's service role can call.

What this doesn't do

  • The Supabase backend is a fixed-window counter, so it can allow up to 2x the limit across a window boundary. Use the Upstash backend if that matters.
  • The SQL was tested in PGlite with stub Supabase roles, not against a hosted Supabase project.
  • No live provider calls were tested. The tests use fakes, not live OpenAI, Anthropic, Stripe, or Upstash accounts.
  • The price table uses standard-tier prices. Batch, flex, fast mode, data-residency uplifts, and tool fees aren't included. Prices change: check the table before you rely on it.
  • Rate limits and spend caps reduce the risk of surprise bills; they are not a replacement for the provider-side limits in the checklist.

FAQ

Is there a monthly fee?
No. You pay $19 once, plus VAT where applicable. The kit runs in your app, on Upstash or your own Supabase Postgres.
What happens if a user calls a model that isn't in the price table?
The call is refused before it reaches the provider, rather than counted as $0. Add the model's prices to PRICES in lib/spend-cap.ts to allow it.
What if a user fires several AI calls at once?
Each call reserves its estimated cost before it runs, and a failed call releases its reservation. That's designed to stop parallel calls from all slipping under the cap together (tested with 20 parallel calls).
Do I need Upstash?
No. Without it, limits run on a Postgres counter in your Supabase project. That counter is fixed-window; Upstash gives you a sliding window.
Has it been run against a live Supabase project or live provider accounts?
Not yet. The SQL ran in PGlite and the provider calls are faked in tests. See "What this doesn't do".
